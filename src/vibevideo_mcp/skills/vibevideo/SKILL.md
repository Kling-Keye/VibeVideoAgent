# Produce a video with VibeVideo

Use the available rendering tools in the project environment. When the brief requests synthetic speech, use an available TTS engine for the requested language and keep the generated clips with the editable project. Preserve supplied narration when the brief calls for it. See [the rendering guide](references/rendering.md) when setting up a new environment or when a required capability is missing.

The coding agent owns the editable project, render commands and creative decisions. Use the tools on actual media whenever a production decision depends on what a viewer sees or hears.

1. **Ground the plan.** Read the brief and identify supplied assets by project-relative path. Call `plan_production` before coding. Pass the original `prompt`, intended `goal`, `deliverables`, and ordered `beats`. Give each requirement an ID, a verbatim `prompt_quote`, an observable claim and the evidence modalities needed. Reference those IDs in each beat. Put discretionary choices in `creative_choices`. Pick a `first_requirement`, a small representative `preview` and the `risk` it addresses. Supply numeric `delivery` constraints only when the brief specifies them. Save the returned `task_id` for every subsequent call. In the paper profile, immediately call `status(task_id)` to activate this saved plan for the current client session. Use `status` to recover it after a restart.
2. **Resolve source questions before committing to a cut.** Use `describe_media` to map unfamiliar footage, `locate_event` to find a moment and refine its bounds, `transcribe_speech` to locate a line, and `inspect_segment` to resolve a detail. Request evidence frames when a visual detail affects an edit. Use `compare_media(reference=..., focus=...)` for a supplied reference. A text-only brief can go straight to a representative render. Read each tool's input schema for its fields.
3. **Render and check the risky decision early.** Use the project's renderer and editable source. A still can establish layout, a moving preview can establish action, and audiovisual timing needs both streams in one excerpt. Call `check_requirement` with the planned requirement ID and `stage=preview`. Set `media.start` and `end` in source seconds. Optional `crop` is source pixels [x,y,width,height]. Returned boxes are normalized [left,top,right,bottom] within the excerpt. Use `timeline_offset` if source time zero maps to a known edit time. Include relevant `source_files` to associate edits with observations.
4. **Revise with evidence.** For a failure, edit the source, render again, and use `compare_media(finding_id=..., media=...)` on the same region or event. For an uncertain finding, adjust coverage, modality or sampling. Inspect affected neighbors when timing shifts. During assembly, check dependencies across cuts, captions, speech or music using `stage=assembly`. Prioritize decisions that a finding can change.
5. **Verify the encoded delivery.** Run `probe_media` on the final file. Choose decode, motion, loudness or silence measurements as relevant. Check critical claims on the final bytes with `stage=final`. Call `register_artifact` with the encoded video, editable files and replayable argv. Include non-generated project assets needed for replay. Then call `submit_delivery` and give the user the returned video path. Report unresolved claims or missing access to semantic perception. If the preview checkpoint was skipped, record why in submission notes. A successful decode and matching file specs establish technical acceptance; describe semantic quality only to the extent supported by the sampled evidence.
